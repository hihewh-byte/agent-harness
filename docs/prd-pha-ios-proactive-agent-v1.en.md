It **does not replace** the harness / startup-stability plans; on conflict: **numeric honesty and fail-closed take precedence over “more proactive” or “more coach-like”**.

## 1. Consensus conclusions (frozen)

1. **Product goal**: What the user opens (or is notified about) is a **proactive, local-first health-management Agent**, not a research prototype that “exports a zip then Q&A in the browser”.  
2. **Evolution path**: Mac PHA (FastAPI + SQLite + harness + optional Ollama) remains the **ledger and audit kernel** over the medium-to-long term; iOS first does **collection + notifications + a display shell**, then whether to move inference onto the phone is decided by compute. Fantasizing that “one PR compiles the Python repo into an App” is forbidden.  
3. **Proactive ≠ clinical care**: What is pushed proactively is **no-LLM fact cards (numeric layer) + rule banding and fixed-template advice (assessment layer) + user-registered reminders**. Diagnostic tone is forbidden; fabricating numbers is forbidden; writing a prescription from a single HRV reading is forbidden. **The proactive path must not use an LLM to write assessments**; spoken Q&A belongs to M3. **“Proactive path” = content generated/pushed without the user triggering it on this occasion** (scheduled notifications, card-level assessment, pre-generation). The user tapping a **button** on the full card to request interpretation is equivalent to “speaking up” and goes through the existing chat harness (TurnEvidencePlan + Numerics audit); it is not the proactive path (v1.6, see FR-6).  
3a. **The proactive agent and Mac PHA are the same product and must not be split**: Fact-card assessment must use **all** comparable history in the Mac ledger (zip import + HealthKit); years of data must not be judged “insufficient baseline” because of a narrow window. Personal baseline looks back progressively by available volume (90 days → 365 days → full history), and the card must state which window was used; beyond personal baseline there is a **general reference layer** (Tier 1 disclosure; only “inside/outside the reference range”, not a medical determination) so the user can make sense of the numbers from day one (v1.6, see FR-2.6 / FR-2.8). **The full zip snapshot is the final ground truth**: import overwrites same-day HealthKit increments; recommend re-importing export.zip quarterly for correction (v1.8). **Second meaning of not splitting (v1.12)**: assessment is “incremental-data assessment against the user’s entire historical background”; **non-numeric memory** the user deposited in chat (self-reported supplements/meds/lifestyle, long-term CHB portrait) is **visible** to button-triggered interpretation, but only as a **non-numeric** Tier1 background (digits stripped, length-capped, not citable as values); situational/session memory (RECALL, turn focus, previous-turn summaries) **does not** enter interpretation; interpretation turns **must not** write any chat-memory table (see FR-6.11 / FR-6.12, M1-P13–P15).  
3b. **Ledger and increments are the same metric set**: same `metric_id`, same day columns, same aggregators; Shortcuts only write new dates. The M1 increment channel remains Shortcuts; an open-source HealthKit App (track B) waits until M2.  
4. **Physical data fact**: Watch data lives only in **iPhone HealthKit**. Real-time / near-real-time = iPhone gateway → PHA on this machine (or the user’s own mesh). Mac **cannot** talk to Watch directly.  
5. **First cut, frozen**: Open **HealthKit samples → Mac `wearable_data` / `wearable_daily`**. Until that is green, do not claim “today’s proactive Agent is live”.

## 2. Problem and users

### 2.1 Current pain (evidenced, not invented)

- Collection: only `export.zip` full import; incremental HTTP already 410. If a fact card existed, freshness = last export.  
- Interaction: answers only when the user speaks; no schedule, no notifications.  
- Form: browser + local Ollama; cannot be a daily product you “just wear a watch” to use.

### 2.2 Target users (v1)

- The maintainer and a few testers who will install TestFlight / Shortcuts.  
- **Not** mass App Store medical users (review, liability, and cloud sync are all unprepared).

### 2.3 Success criteria (product, not vanity)

| Signal | Pass bar |
|--------|----------|
| Pipeline | Without zip, Watch-side HRV/sleep/steps can enter the Mac store, with `source=healthkit` |
| Proactive | When the user has not opened chat and has not opened the Mac browser, **iPhone can pop a local notification**, copy from a no-LLM fact card (rule banding + fixed template) |
| Honesty | Card shows `as_of`; if expired, mark stale; do not pretend “this very moment” |
| Red line | No new diagnostic titles; no precise numbers outside the manifest; non-medical-device copy retained |

## 3. Product form (phased; skipping levels forbidden)

```text
Watch → iPhone HealthKit → [Shortcuts | iOS App]
                              ↓ HTTPS/HTTP + token
                         Mac PHA ingest
                              ↓
                    SQLite ledger + C-layer audit
                              ↓
              Fact-card engine (no LLM: numeric layer + rule assessment layer)
                              ↓ GET /proactive/fact-card
              iPhone Shortcuts / automation → system local notification
              M2 App UI shows the same JSON; chat (harness) ← LLM only when the user speaks
```

| Phase | What the user sees | Where compute lives |
|-------|--------------------|---------------------|
| **M0** | No new UI; today’s Watch numbers in the store | Mac |
| **M1** | **iPhone local notification**: fact-card numbers + template advice | Mac generates JSON; iPhone pulls the card and notifies |
| **M2** | iOS App: auth, sync status, **the same fact card**, reminder registration | Collection on iOS; ledger on Mac |
| **M3** | App wired to the **same** interpret/Q&A API (capability already landed on the full-card web page by M1-P9; M3 is only App UI wiring) | Default still Mac; on-device LLM **opens a separate task card** |
| **M4** | Optional: some PHA core on-device | Only when M2 is stable and there is a clear compute plan |

**The v1 product commitment stops at M2.** M3/M4 are not this PRD’s DoD. **M1-P9 “button-triggered interpretation” is not doing the M3 App early**; it hangs M3’s capability (user speaks → Mac harness answers) on the full-card web page first; M3 therefore shrinks to wiring. Sequence unchanged (trigger is still M2 stable).

## 4. Scope

### 4.1 In scope (v1)

- `POST /ingest/healthkit` plus idempotent writes and same-day daily-table rollup  
- iOS Shortcuts validation, then a thin native App (HealthKit + sync + notifications)  
- No-LLM daily fact card: `as_of=MAX(day)` + **take values per registry `temporal` and explicitly write the actual date / as-of time (empty only if past the window; do not label a non-today value as today)** + **progressive personal baseline (90 days → 365 days → full history; the card states which window was used)**; rule banding  
- Fact card two layers: ① numbers / `as_of` / `stale` ② rule banding + **general reference layer (Tier 1 disclosure)** + **fixed-template advice** (not LLM)  
- **My assessment requirements** (user free text, stored in local prefs) + **button-triggered interpretation**: after tap, generated via the existing chat harness, Numerics-audited, shown in an independent block, cached by (date + requirements hash); not in notifications, not pre-generated  
- HRV column semantics correction: zip-imported `hrv` samples’ `sample_id` prove they are all Apple SDNN; the `hrv_rmssd_ms` column must be renamed/migrated to the SDNN series (single card, stacked with harness ACK)  
- M1 proactive channel: **iPhone Shortcuts local notification** (scheduled automation pulls `GET /proactive/fact-card`). APNs remote push is not v1  
- Meds/supplements: **only user-registered schedules** → local notification  
- `as_of` / `source` disclosure  
- LAN or Tailscale; ingest token

### 4.2 Out of scope (v1: forbidden to sneak in as a requirement)

- Watch standalone App, second-by-second in-workout coach  
- Cloud storage of health data, multi-tenant SaaS  
- Diagnosis, medication dosing advice, supplement efficacy claims  
- Runtime LLM self-heal, automatic catalog writes  
- Changing the harness-core product narrative back to “this repo is a health App” (public README first screen unchanged)  
- Using screenshot OCR to impersonate live collection  
- **Proactively pushing LLM health assessments/advice** (belongs to M3 spoken Q&A, or a separate task card)  
- **LLM interpretation “daily auto pre-generation”**: would turn FR-6 back into a proactive path; if needed, open a separate decision and register in §11; default is not to do it  
- Letting LLM interpretation bypass the chat harness and call Ollama directly (“running naked”); precise numbers in interpretation that are outside facts / baseline  
- Letting fixed-window wearable summaries (`WEARABLE_90D_SUMMARY`) enter the fact-card interpretation path  
- APNs / third-party push cloud (v1 uses iPhone local notifications)  
- **Replacing the `/api/chat` harness as the conversation kernel with LibreChat / Open WebUI / AnythingLLM etc.** (their own routing, RAG, and tool loops would bypass TurnEvidencePlan and Numerics audit). If the Mac web chat is reskinned, it must be a thin client of that endpoint (v1.14)

### 4.3 Relationship to zip import

zip is **kept** for cold start / moving. HealthKit is the increment channel. Full zip **does not delete** `healthkit|` rows; after import, recompute by day; steps take the max of per-source sums. Details in the change-log.

### FR-2 Fact-card engine (no LLM)

| ID | Requirement | Acceptance |
|----|-------------|------------|
| FR-2.1 | Read `MAX(day)` + **metric rows valued by `temporal`** + mean/min/max/percentiles over the **progressive baseline window** | Script emits JSON; numbers ⊆ query results; JSON writes `baseline_window` (`90d` / `365d` / `all`) and `baseline_n`; rows write actual `day` / `freshness` / `partial_day` |
| FR-2.2 | Banding for HRV etc. is rules only (e.g. vs percentiles); copy templates are fixed; `partial_day` is unbanded | No model process |
| FR-2.3 | Stale: `as_of` earlier than the local calendar day → `stale=true` | Visible on the card; notifications must say “not today”; labeling the last day as today is forbidden |
| FR-2.4 | Card has two layers: `facts` (numbers) and `assessment` (rule banding + template advice + disclaimer) | JSON has both layers at once; assessment sentences contain no diagnosis/prescription |
| FR-2.5 | JSON / full card enumerate **user-selected** registry metrics; no record writes “none”; omitting a row or substituting another day’s value is forbidden | Every selected item appears; unselected items do not; the default five can be changed by the user |
| FR-2.6 | **Card-level assessment (rewritten in v1.6)**: coverage + stale + **progressive personal baseline** banding + one advice sentence. Baseline window steps by available volume: last 90 days with ≥ 7 days → use 90 days; else last 365 days with ≥ 7 days → use 365 days; else full history with ≥ 7 days → use full history; only if all three are &lt; 7 write “history short n/7”. **Merge only under the same definition**: zip-era and HealthKit sleep total / deep / REM / awake union definitions match, treated as one series; if `sleep_core` / `in_bed` history is empty, honestly write “no history”. Card-level composite three bands (easier / even / favoring) are a percentile vote of sleep total, HRV, and resting heart rate vs personal baseline; any missing item writes “no composite” rather than guessing. Analysis = relative to self, not an LLM long essay | `assessment.summary` includes a window gloss of the form “vs your last 12 months, 268 nights”; `baseline_short` appears only when all three windows are &lt; 7; selfcheck covers 90d empty → 365d hit |
| FR-2.7 | Metric set is user-specified; a Python hard-coded dead list is forbidden | `GET/PUT /proactive/fact-card/prefs`; grouped checkboxes at the bottom of the full card; allow-set = registry `fact_card.eligible`. Card = checkboxes. Coverage denominator = checked items with `coverage_denominator != false` (VO2max is sparse and does not count in the denominator) |
| FR-2.8 | **General reference layer (Tier 1 disclosure)**: beyond personal baseline, metrics that **have population-reference meaning** get one in-range / out-of-range line, format following the T1 disclosure block of `manifest-tier-v1`: `【参考标准】<描述>（来源：<指南/组织>，请自行查证，非医疗建议）`. Reference ranges are **data**, in registry `fact_card.reference_range` (low/high/unit/source); Python does not hard-code the numbers. v1 applies to: sleep total, resting heart rate, steps; **does not apply**: absolute HRV (too much individual variance; compare only to self), awake, in bed, **deep/REM share** (the user can compute from stage hours; fabricating a population range before a sourced guideline is forbidden) | Full card: one extra reference sentence per applicable metric; numbers ⊆ registry; `fact_card_numeric_atoms` includes reference ranges in the atom set; non-medical wording; HRV / deep-sleep share / REM share have no reference sentence |
| FR-2.9 | **My assessment requirements**: the full card has a free-text box; the user writes “what I want to focus on / what tone / goals I care about”; stored as `assessment_prompt` in `data/fact_card_prefs.json` (on this machine, not leaving the device circle). v1 is **save + echo only**; the rule layer does not parse it (the rule layer does not change because of it); it is an input to FR-6 interpretation | `GET/PUT /proactive/fact-card/prefs` gains one field; refresh echoes it; empty string is legal |
| FR-2.10 | **Metric temporal semantics** | `temporal.kind ∈ {accrual, daily_lagged, overnight, rolling_mean, latest}`. The card takes values per the declaration and writes the actual `day`. Both `overnight` and `daily_lagged` look back within `freshness_days` (overnight metrics default 2 days). `latest` is the most recent sample in the lookback window (VO2max default 90 days), labeled “most recent”, and does not count toward coverage. `accrual` in progress today is unbanded. **Copy domains (v1.14)**: `partial_day` / `advice_partial` only mean “today’s accrual is not closed”; `hk_ok` / `hk_none` / `sync_*` only mean ledger/sync status. An accrual row that has a value must not render “not on the Mac / still on the phone”. Language tables are by kind; writing a template for a single `metric_id` is forbidden |

### 5.1 Fact-card content contract (v1.3 · the full card must obey)

The proactive channel is not “fling out whichever item has a number”. What the user wants to see is **their selected fact list + assessment/advice**. Analysis on the proactive path **allows rules only**: relative to personal **progressive baseline** (90 days → 365 days → full history) + general reference layer (Tier 1 disclosure); LLM-written commentary is forbidden. LLM interpretation appears only after the user taps the button, in an independent block (FR-6).

| Block | Must appear | Forbidden |
|-------|-------------|-----------|
| **Facts** | Every user-selected metric appears: with a number write number+unit, without a number write “none”; `as of as_of`; stale writes “not today” | Substituting yesterday for today; fabricating numbers not in the store; stuffing unselected items onto the card |
| **Assessment** | Coverage (how many selected items have numbers); name the missing items; each item writes **baseline window + n** (e.g. “vs your last 12 months, 268 nights”); write “history short n/7” only when all three windows have n&lt;7; otherwise below / even / above personal percentile; card-level composite three bands or “no composite” | Diagnosis, etiology, pathology titles; declaring “insufficient baseline” just because the 90-day window is empty |
| **Reference** | Each selected metric that has registry `reference_range` gets one line `【参考标准】…（来源：…，请自行查证，非医疗建议）`, plus “inside/outside the reference range” | Population range for absolute HRV; diagnostic conclusions from the reference layer; Python hard-coded numbers |
| **Advice** | One fixed template: missing items → sync first; any below baseline → easier schedule; otherwise even / favoring | Training prescriptions, supplement efficacy, medication doses |
| **Disclaimer** | Fixed: educational reference, not medical advice, cannot replace a physician | Lengthened legal copy |
| **AI interpretation** (only after the button) | Title “AI interpretation (experimental) · not medical advice”; generation time, model name; body Numerics-audited | Mixed into the rule layer; in notifications; pre-generated; outside precise numbers |

**Data completeness**: the M0 Shortcut currently POSTs **steps only**. Selected items not yet in the store must be marked “none”; do not pretend the assessment is complete. To make assessment real, **FR-1.5 multi-metric ingest** is required (task card **M1-P5**, from v1.7 changed by **M1-P11** to full-set sync): for every registry metric that has `shortcut_health_type` and ∈ FR-1.4, accrual types POST the same “one same-day total number” as steps; once-per-day types POST samples with dates. Accrual types should not Find raw sample lists. Fabricating numbers when not ingested is forbidden.

**Two reach layers**:

| Layer | Duty |
|-------|------|
| Lock-screen notification | Short teaser: as-of / whether today / coverage / “open full card”. iOS truncates long bodies; stuffing the list into the notification to fight truncation is forbidden |
| Full card | `GET /proactive/fact-card/view`: list + assessment + advice + disclaimer + **metric checkboxes**. Numbers ⊆ JSON |

Default checks may be registry `enabled_default` (currently: steps / HRV / sleep / resting heart rate / active energy). **Default ≠ unchangeable.**
