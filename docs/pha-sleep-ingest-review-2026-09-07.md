## 3. 「睡前 2 小时被算进清醒」是怎么发生的

这不是 PHA 的 bug，也不是健康 App 的 bug，是 **Apple 对 Awake 的定义**：

- Watch 睡眠会话从「睡眠专注模式开启 / 到达日程就寝时间 / 检测到上床」开始；
- 会话内没被判为任何睡眠分期的时间 = **Awake**；
- 所以「上床 20:30、真正睡着 22:45」→ 20:30–22:45 记为清醒 ≈2.2h。9/7 截图正是这样：Awake 3h35m 里有一整块在入睡之前，而 Time in Bed 8h57m **没**把它算进去（入睡 7.72 + 清醒 3.58 = 11.30 ≠ 8.95）。

维护者侧可核对：健康 → 睡眠 → 完整日程 的就寝时间是否比实际入睡早；或睡眠专注模式是否手动提前开启（在床看手机/看书）。这不影响 PHA 的正确性要求：PHA 必须原样接受 Apple 的清醒总数，但要拆开命名。

**维护者口径（2026-09-07 12:34 / 12:37，覆盖本文 v1 的「三分解」提案）**：健康 App 里没有「入睡前」这个概念和数据；睡眠从入睡开始算，核心/REM/深睡计入入睡，清醒不计入。9/7 的会话是从 **20:30 左右一段 4 分钟 Deep** 开始的（截图 Deep 行最左的细线），之后 ≈2.2h 清醒，22:45 才真正入睡。按 Apple 规则「入睡后未睡着 = 清醒」，**App 算得没错，规则也没错**；错的是那 4 分钟深睡本身（手表误判），属于**采集错误**，不为它发明产品字段。

**维护者口径补充（12:42）**：不需要 PHA 去找出采集失误再修正，用户自己修正即可。人的睡眠数据本来就千差万别，**PHA 无法判断某一夜异常不异常**，也不该给某夜打「采集错误」标签或把它排除出基线。PHA 能做、也应该做的是：**跟用户以往相比数据偏离时，主动提醒用户「数据与以往不同，请检查」**——用户未必知道数据异常和它表示的意义，这正是做主动健康提醒 agent 的原因。

据此 PHA 侧规则：

- 所有睡眠列 = 健康 App 原值（入睡 = 核心 ∪ 深睡 ∪ REM 一次总并集；清醒原值；在床只取 In Bed 样本），不拆、不删、不改、不排除。
- 不新增派生产品列；**不加 `collection_anomaly` 之类的判定标记**（本文早前两版提案作废）。
- 事实卡对睡眠各项走与步数/HRV 相同的既有机制：与个人近 90 日基线比（n ≥ 7 才分档）。**偏离基线时通知文案加一句固定模板**：「清醒 3.6h，明显高于你近 90 日的水平，请到健康 App 核对这一夜的数据」。是提醒核对，不是断言错误；用户核对后若在健康 App 修改，下次同步自然覆盖（日键 UPSERT）。
- 9/7 这种夜就会触发这条提醒；PHA 到此为止，不做进一步判断。

## 4. 错误清单与解决方案（按严重度）

### A. 跨分期重叠被重复计入（数据正确性 · 最高）

- **现状**：`sleep_stage_hour_samples_from_lists` 对每个分期各做区间并集再相加。分期之间的重叠不去重。
- **正确规则**：入睡总时长 = **所有睡眠分期段（Core/Deep/REM/Asleep）的一次总并集**；各分期小时数只在「单来源、互斥」前提下才有意义。
- **方案**：
  1. 分段落库（§B）后，入睡总并集复用 zip 路径已存在的 `compute_sleep_hours_union`（含 Watch > iPhone > 其他 的来源优先级）。
  2. 若 `Σ各分期` 与 `总并集` 相差 > 5%，响应与日志打 `stage_overlap=true`，各分期列**不写**（写 NULL），只写入睡总并集；事实卡对分期显示「分期有重叠，未采信」。宁缺毋错。
  3. 捷径增取 `Source`/`Device` 字段（Get Details 是否提供需真机确认），有来源就按优先级只留一个来源的分期。
- **验收**：任何一次入库，`入睡 + 清醒 ≤ 会话跨度 ≤ 采集窗口长度`；自检加「两来源重叠分期」用例。

### B. 只落总和、不落分段、成功不留审计（可追溯性 · 高）

- **现状**：`PHA_SLEEP_V1` 解析后直接求和写日键行；成功时日志只有「empty timestamp; using received_at」四行；拒批预览 400 字符（今日已放宽到 8000，仍非结构化）。要回答「13.3h 从哪来」，现在**无数据**。
- **方案**：
  1. 分段写入已存在的 `wearable_sleep_segments`（列：`day,start_time,end_time,source_name,sample_id,is_awake`），`sample_id` 用 `healthkit|{user}|{stage}|{start}|{end}|{source}`，幂等；分期名放进 `sample_id` 第 4 段以便 `sleep_stage_kind_from_sample_id` 复用。
  2. 日表全部从分段重算（zip 路径已有 `sleep_metrics_from_segment_rows`），不再直接落「分期小时数」日键行。旧的 `sleep_core/…` 日键 POST 路径保留为兼容，但同一天有分段时以分段为准。
  3. 成功响应与日志打一行结构化审计：`kept / skipped_zero / dropped_unknown_label / per_stage_h / union_asleep_h / session_span / window / stage_overlap`。手机「显示结果」把这行原样显示，维护者当场就能和健康 App 比。
- **回滚**：分段表已存在，不新增 schema；停用只需不写该表。

### C. 窗口规则口径不一（契约漂移 · 高）

三处三个说法：

| 位置 | 口径 |
|---|---|
| 任务卡「跨夜规则」 | 醒来日 D 的睡眠 = 与 `[D-1 12:00, D 12:00)` 相交的分段；**禁止**只用 `is today` |
| 服务端 | 与 `received_at` 往前 24h 重叠的分段；日键 = `received_at` 日历日 |
| 捷径 | `Start Date is today`（午夜前全丢） |
| PRD M1-P6 行 | 「昨午–今午窗口」「待真机 Allow Access」（均已过时） |

- **方案**：以任务卡口径为唯一规范，改两处实现口径（下一步编码时做）：
  - 服务端：**醒来日 D 由数据推导**（= 最后一段睡眠分期结束的日历日），不用 `received_at`；只保留 `[D-1 12:00, D 12:00)` 内的分段；若数据推导出的 D 早于 `received_at` 日历日 1 天以上，返回 `stale_sleep_bundle` 让用户知道拿到的是旧夜。
  - 捷径：见 §D。
- 本次已把 PRD/任务卡改成一致（见文末改动清单）。

### D. 采集窗口：`is today` 丢午夜前，`last 1 day` 会崩（采集可靠性 · 高）

- **现状**：`last 1 day` + Get Details 在真机上 *problem running*（Shortcuts 大列表已知问题）；`is today` 能跑但丢午夜前 In Bed 与分期，9/7 清醒少了 0.67h。
- **候选方案（每次只试一个，真机验证后再写进卡）**：

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **D1（推荐先试）** | Find Sleep，按 Start Date **降序**，**Limit ≈ 150** | 体量有上限不会崩；最近一晚必在最前 | 一晚分期 60–100 段 + Awake 段，150 可能截掉夜初；需按真机段数调 |
| **D2** | 两次 Find：`Start Date is yesterday` + `is today`，各自 Get Details，正文合并 | 复用已通 XML | yesterday 含前一晚尾巴 + In Bed，列表可能又大到崩 |
| ~~D3~~ **已否决** | 在床 = 会话跨度推导 | — | 9/7 真值：在床 8.95 ≠ 入睡+清醒 11.30。Apple 的 In Bed 不含入睡前那块。**在床只能来自 In Bed 样本**，取不到就写空；另加派生列 `sleep_period_h`（首段睡眠开始 → 末段睡眠结束），不写进在床 |

### E. 偏离基线时未提醒用户核对（产品价值 · 中；按维护者口径定稿）

见 §3。方案：不拆清醒、不加产品列、不打异常标签、不排除任何一夜。睡眠各项进入事实卡既有的个人基线分档；偏离时通知加固定模板「…明显高于/低于你近 90 日的水平，请到健康 App 核对这一夜的数据」。PHA 只提醒核对，不判定对错、不修正。所有列始终等于健康 App 的值。

### F. 校验粒度过粗（fail-closed 用错地方 · 中）

- **现状**：一段 20 秒的分期被 Shortcuts 取整成 end==start，整晚 400；今日改为跳过 0–2 分钟零时长。
- **规则化**：**结构性错误**（三列表长度不一、标记缺失、时间戳不可读、倒序 > 2 分钟）→ 整批拒；**装饰性瑕疵**（零时长、未知标签）→ 按段跳过并计数，计数进审计行。fail-closed 是「不编数」，不是「一段坏全晚扔」。

### G. 半截 POST 残留无清理路径（数据卫生 · 中）

- **现状**：9/6 日表 `in_bed_hours=0.728` 来自 19:41 一次半截 POST，不是真值，会进 90 日基线。
- **方案**：
  1. 规则：睡眠 bundle 成功写入某醒来日 D 时，**清掉 D 的所有 `healthkit|…|sleep_*` 旧日键行**再重算（现有按单指标 replace 扩到整个睡眠家族）。
  2. 一次性清理：维护者删除 `healthkit|default|sleep_in_bed|2026-09-06|healthkit` 并重算 9/6（操作步骤写进任务卡；不算代码改动）。
  3. 事实卡：`in_bed_hours < 1h` 且无分期 → 显示「无」而不是 0.7。

### H. 手机侧无回执（可运维性 · 中）

- **现状**：12:13 重跑，Mac 无 POST，维护者不知道；PRD §10 已要求「UI 必须显示上次成功时间」但无接口。
